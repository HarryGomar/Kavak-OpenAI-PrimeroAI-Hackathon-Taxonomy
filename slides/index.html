Hill-climbing is hard, and continual learning is not a solved problem. Evals are what drive performance. In our last project a loop improved its own rules and climbed its own eval, an LLM judge, from 78% to 87%. When we checked by hand afterwards, it had gone from 81% to 84%: a third of the gain. 15 of the 48 changes it kept made our labels worse. Where a task checks itself, a loss or a test suite, that's enough: Karpathy's autoresearch hill-climbs on its own. Most useful tasks have no such check. So the eval itself needs a method to improve: what counts as right, and how we check it. That's what this talk is about.

The task we tried this on comes from our own work. To understand a market you have to match and connect its listings into product trees: Oreo, Double Stuf, Golden; Lattafa, the Khamrah family, Khamrah Qahwa. Until you know listings are one product you can't add up its price, its reviews or its demand. It looks trivial for a person and is surprisingly hard for an agent: a size or a 12-pack is never a new product, a flanker like Khamrah Qahwa is.

We don't even know if we are improving, and we want this to work across domains without starting from zero each time. That's why we want rules: they are free, you can read and test them, and they carry over. Each constraint is one part of the system.

Taxo: a solver, and three loops that improve it.

We propose this architecture. One domain opened up on the left; across domains on the right. In the middle the solver: listings go through free rules, and an agent gets only what they can't settle. Loop 1 above: errors on the gold set, an agent proposes a rule, a gate in code keeps it only if F1 on gold rises. Loop 2 below: a validator checks listings nobody labelled, a person labels what it flags, and that goes back into the rules and the checks. Loop 3 on the right: what worked is distilled into lessons for the next domain. We'll go through each loop with an example.

Lattice

khamrah ×5 · khamrah qahwa ×2

# rules/fragrance/route-no-barcode.yaml
when:
  - {fact: listing.barcode, missing: true}
  - {fact: placement.level, eq: brand}
then: {route: agent_evidence}
Loop 1 starts from cases we labelled by hand, and induction turns them into rules. Each rule is a file you can read. Here is one title. The vocabulary file says which words are variants: "Eau De Parfum 3.4 Oz Unisex" is stripped, leaving khamrah qahwa. The registry file holds Lattafa's official lines, found once by an agent with web search and written down by code: Khamrah Qahwa is in it, so the listing is placed with no agent call. If it hadn't been, the lattice counts names across the brand's listings, and a route file sends whatever is still unclear to the cheapest agent that can settle it.

Loop 1: the lattice finds products by counting.

No word lists. A run shared by two products is a family. Add a word to the vocabulary and the count changes on the next run.

This is how the lattice works, on six Lattafa titles. First strip the brand and the variant words. Then count every run of words across the brand's titles: khamrah appears in five, khamrah qahwa in two, khamrah dukhan and yara in one each. Each title joins its longest run seen at least twice. That gives two products, Khamrah and Khamrah Qahwa, and because they share "khamrah", Khamrah is a family. Dukhan and Yara are below the floor: the registry settles them if it knows them, otherwise an agent does. No word lists are involved.

Loop 2, validation: improve the eval itself.

  1. A validator agent runs on listings nobody labelled.
  2. It flags errors, and cases it isn't sure about.
  3. A person labels them, and what counts as right gets sharper.
  4. It asks what's going on, and that becomes a rule and a stricter check. [example from the run]

F1 of the solver as the checks get stricter

A small gold set doesn't cover everything, so loop 2 checks the solver on listings nobody labelled. A validator agent raises errors and cases it isn't confident about, and brings them to us to label. We change the labels. Then it asks what is going on: for example [confirm from the run: small houses with no barcode name the product only in the description]. That goes back into the rules, and into a stricter check, so confidence goes up. On the graph: as the checks get stricter, rule set 1 falls from [x] to [z]; after refining, rule set 2 gets back to [w]. We improve two things at once: the validation, and the solver underneath it.
